# ArcGraph 0.2.0 changes and compatibility

ArcGraph is a local-first code semantic graph engine. 0.2.0 is beta software (PyPI classifier
`Development Status :: 4 - Beta`). It was published on PyPI on 2026-10-21; the two uploaded
files are byte-identical to the validated candidate built from commit
6f5cd85c40774990838dbf62b9ae7f80af0feb64 (wheel sha256
`831c6222a84638cfef037028faba381c00fa4c9b9fcd242845711d6f2887709e`, sdist sha256
`25cbe2502dd7cd35d069678945691817a10f6beb1659018225a2dde0bdaf980b`). Later commits on `main`
are not part of the uploaded files. It contains everything in
[0.1.0](v0.1.0.md) plus the changes below, made on `main` after the commit the 0.1.0 files were
built from (4a6748b1ddee23755dae1f91647b90efcda0175f). A version label alone is not proof of
package publication, platform support, or source/artifact identity. Use
`arcgraph version --json`.

## Upgrading

- **Rebuild required.** The internal layout of `index.sqlite` changed (storage version 1). An
  index built by 0.1.0 is refused with "ArcGraph storage version mismatch: index has 0, runtime
  expects 1. Rebuild required. Run arcgraph build." (error code
  `ARCGRAPH_SCHEMA_VERSION_UNSUPPORTED`, exit 2). There is no automatic migration. Query results
  on a rebuilt index have the same shape as before; the read schema and the index schema `1.0.0`
  are unchanged.
- Rebuild change-safety baselines as well: plain call edges, the change-safety projection and
  its profile changed, and a comparison across projection profiles is refused with a request to
  rebuild under the same configuration.
- Python 3.11 to 3.14 are supported (`requires-python >=3.11,<3.15`); 0.1.0 on PyPI kept
  `>=3.11,<3.13`.

## Graph exports

- **Behavior change.** `arcgraph build` and `arcgraph sync` no longer write `nodes.jsonl`,
  `edges.jsonl` and `semantic_facts.jsonl`. `arcgraph --output-dir OUT export` writes those three
  files into the current build with the same names and record format as before.
  `diagnostics.jsonl` is still written by default.

## Python call analysis

New indexes of the same code can contain more resolved call edges, other targets for some
edges, and fewer edges that pointed at a method the receiver does not have. The analyzer now:

- types receivers from more evidence: pathlib results, builtins and documented standard library
  results, display elements and literal receivers, generator expressions and generator
  functions, callable annotations, factory return annotations read in their defining scope,
  operator annotations, overload families (the runtime implementation), and annotated attribute
  chains;
- follows control flow: bindings are read where the call is (module, class body and function
  scopes, star imports, imports only type checkers run), values are narrowed to not `None` by
  `assert`, branches, `match`, `try`, `while x is None:` and `and`/`or` chains, and a value is no
  longer typed past an unknown write or a rebinding;
- finds inherited methods through the method resolution order, including catalogued external
  bases and `super(C, obj)`;
- leaves a call unresolved instead of guessing when the evidence is missing: a receiver typed
  `Any`, a local value that hides an import or a builtin, a name that may be unbound at the call,
  or a method the known type lacks;
- emits every candidate of a conditional branch.

Name-based guesses remain `heuristic` edges. A new confidence profile, `evidence_only`, leaves
them out: pass it as the confidence profile (`--profile`) of `callers`, `callees`,
`impact`, `context`, `explain` or the `report` commands; the
MCP tool `arcgraph_entrypoint_flow` now takes a `profile` too. `arcgraph ci` adds `verified_resolution_rate`,
`verified_resolved_callsite_total` and `verified_resolution_scope` next to the existing rates,
whose definitions are unchanged.

Specific target changes worth checking in saved queries:

- An SQLAlchemy `Result.all()`, `fetchall()` or `fetchmany()` is a `Sequence`: `append` or `sort`
  on it is no longer resolved, and `count` / `index` resolve to `collections.abc.Sequence`.
  `Connection.execute(...)` yields a `CursorResult`, so `yield_per` and `close` resolve to its own
  methods. `Session.commit` resolves to its defining module's name rather than a public re-export.
- An import inside a function is used only where it has surely run: after an `if`, `with` or
  `finally` that may skip it, the call is left unresolved, while an import in `try` whose
  handlers all leave (`return`, `raise`, `continue`, `break`) is used after the `try`.

## Project environment and Python structure

- Definitions of external dependencies are read from the analysed project's own environment:
  `[tool.arcgraph] python_environment`, otherwise the project's `.venv`. ArcGraph's own
  interpreter, an ambient `VIRTUAL_ENV`, executable `.pth` files and editable finders are not
  used. The environment used is recorded in index metadata; a change to it makes the index stale.
  `arcgraph doctor` reports it as `project_dependency_environment`.
- Python structure is parsed by the project interpreter when one is available; otherwise ArcGraph
  falls back to parsing with its own interpreter. `summary.toolchain_status.python_structure`
  reports status, interpreter, version, reason and fix. Failed reads share a 60-second budget per
  build or sync/watch update. This status is not a warning and does not change diagnostics or CI
  checks.
- `arcgraph trace run --python PYTHON` runs pytest traces with the project interpreter (probed
  from the project environment when omitted); the project does not need ArcGraph installed.
- `--coverage` also accepts coverage.py JSON with test contexts.
- Documents of a `--scip-index` input are rebased on the project root its metadata declares, so
  files with the same relative name under different targets no longer collapse.

## Optional semantic core (pyright)

- New and **off by default**. Enable it per project with `[tool.arcgraph] semantic_core = true`
  after `arcgraph setup semantic` (installs pyright 1.1.414 from npm, verified by SHA-512) or
  `arcgraph setup semantic --from LOCAL_TGZ` (offline). Node.js 14 or newer and a project Python
  interpreter are required.
- When enabled, admitted pyright answers become supports of the same public call graph;
  lambdas, generator expressions and comprehensions with their own scope appear as anonymous
  function identities (`fn#…`). An analyzer external target that an admitted pyright answer does
  not support is kept with resolution status `conflict`.
- `summary.toolchain_status.semantic_core` reports `disabled`, `active`, `partial` or
  `unavailable` with pyright version, Node, reason and fix; `arcgraph doctor` explains a fallback.
  Files without semantic results keep the existing analyzer's results.
- Sync with the semantic core enabled: an unchanged tree returns unchanged in about
  3 s; otherwise the reindex result reports reason `semantic_core_incremental`
  when checked responses were reused and `semantic_core_full_build` when none were.
- Time and memory: on the mealie project used in our measurements a full build with the semantic
  core takes about 145 s and peaks at about 1.9 GiB
  (without it about 16 s); on this repository about 260
  s and 3.4 GiB.

## FastAPI and frameworks

- FastAPI class-based routes appear in routes, the graph, MCP and impact results, pointing at the
  method node; both the local registration and the mounted route are kept. Route properties add
  `parameters`, `self_injection`, `path_scope` and `path_status`; an unknown prefix is not shown as
  a served path.
- Unannotated `Depends` parameters take the provider's annotated type (a generator provider's
  `yield` type); an unannotated class attribute `x = Depends(f)` is left untyped, as FastAPI does
  not inject it.
- Route decorators that no route is made of are reported.

## Change safety, sync and output

- `arcgraph change` no longer reports pure position changes as semantic changes: inserting a
  blank line or moving a function leaves the semantic diff empty, with the position kept in the
  location evidence. This applies with the semantic core off as well.
- Sync no longer drops what a full build of the same tree writes: TypeScript external symbols and
  packages, and Python receiver narrowings, are kept after a sync.
- Summary warnings and the 200-entry diagnostics sample are ordered by content, independent of
  sync history.

## Known limitations

- The semantic core misses its original budget (mealie cold build within 30 s and 1 GiB), which is
  why it is off by default.
- With the semantic core enabled, a one-file change syncs in about 94 % of a
  full build: mapping, admission and projection are recomputed in full. An unchanged sync still
  re-checks modules that share a short name across source roots, and a change to a workspace module
  whose name matches an absolute import of the typeshed stubs or the environment re-collects all
  semantic results.
- The semantic core's threat model does not cover a user who rewrites the index database together
  with its manifests. A process of the same user can still race the private pyright copy; on
  Windows, making the copy read-only does not freeze its directory entries.
- Function-local imports are not used after a plain `with` block, outside a `while True:` loop left
  after the import, through `global`, or from a nested function; a callable alias assigned inside
  `try` is a heuristic target only.
- ArcGraph's own self-index quality targets were lowered to 0.94 (overall) and 0.90 (attribute)
  after the analyzer work in this version reached 0.9408 and 0.9010, short of the earlier 0.945 and
  0.91; analyzer work on the remaining gap continues after 0.2.0.

## For contributors

- The unshipped semantic prototype (`arcgraph/semantic_prototype`) was removed; the sdist no
  longer carries it.
- The test suite runs in parallel with pytest-xdist (`-n auto` in CI); pytest-xdist is a
  development dependency. CI provisions the locked pyright for semantic tests.
