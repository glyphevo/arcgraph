# ArcGraph 0.3.1 changes and compatibility

ArcGraph is a local-first code semantic graph engine. 0.3.1 is beta software (PyPI classifier
`Development Status :: 4 - Beta`). It is declared on `main` and not yet published; its publication
status is kept in the [release notes index](../../RELEASE_NOTES.md) only. It is a patch for
[0.3.0](v0.3.0.md): it contains everything in 0.3.0 plus the fixes below, made on `main` after the
commit the 0.3.0 files were built from (32a83c9ab63f8e753cbbf5991927f9194ce3acf8). A version label
alone is not proof of package publication, platform support, or source/artifact identity. Use
`arcgraph version --json`.

## Upgrading

- The index storage version (1) and the read schema (1.4.0) are unchanged; an index built by 0.3.0
  still opens.
- A Django project whose build failed in 0.3.0 with "merged graph has N dangling edge endpoint(s)"
  builds after upgrading; run `arcgraph build` once.

## Fixes

- **Django URL patterns no longer abort the build.** In 0.3.0 a `urls.py` with
  `RedirectView.as_view()`, `admin.site.urls` or a decorator-wrapped view such as
  `login_required(view)` made `arcgraph build` exit with code 2, because the Django adapter emitted
  route edges to handler nodes it never created and the merge step rejected the whole graph. The
  adapter now creates an unresolved placeholder node for a handler, class or attribute path it
  cannot resolve (the same representation as an unresolved `include()` target), and the merge step
  no longer aborts on an adapter-produced edge whose endpoint is missing: the edge is dropped and
  recorded as an `adapter_dangling_edge` diagnostic (counted in `warning_count`). Edges produced by
  the Python and TypeScript analyzers are still validated strictly. **Behavior change:** a defect
  in any framework adapter now degrades to a diagnostic instead of failing the build.
- **`arcgraph tests` recommends the tests that actually cover the target.** When the index holds
  per-test coverage edges that point at the target itself, only those tests are recommended;
  the module-level coverage edges (every test that executed some line of the target's file) are
  used only when no direct edge exists, with the reason `runtime coverage covers target module`.
  In that case `coverage.edges` and `coverage.covered_targets` in the JSON output list only the
  direct edges. Keys are unchanged.
- **`arcgraph precision scip-python --target-only DIR` no longer fails on files outside DIR.**
  scip-python indexes files that DIR imports from elsewhere in the repository (for example
  `scripts/semantic_shadow.py` when DIR is `arcgraph`); 0.3.0 rejected them with
  "SCIP document path escapes its project root". Such documents are now rebased relative to the
  repository root; a document outside the repository still raises that error.

## Known limitations

- An adapter edge dropped as dangling is not restored by an incremental reindex that only adds the
  missing target file; a full build restores it. The common order (a `urls.py` that imports its
  views module, then the views module) is restored incrementally.
- A `urls.py` whose only reference to a module is a string `include('app.api.urls')` keeps its
  `includes_router` edge unresolved after an incremental reindex adds that module; a full build
  resolves it.
- Test methods inherited from a base class defined in another file have no test node, so a
  coverage context for such a test does not match (the remaining unmatched contexts on projects
  that use shared test base classes).
- With several `--target-only` directories, SCIP documents that rebase to the same repository
  path are merged by last writer; the single-directory command is unaffected.
- The limitations listed in [0.3.0](v0.3.0.md) still apply.
